# abr-batch

デジタル庁の「アドレス・ベース・レジストリ」（住所の公式データ）を MySQL に取り込むバッチです。
素直に書いた遅い版から始めて、計測しながら段階的に速くしていった過程を残しています。

## 結果のまとめ

東京都の住居表示データ 1,752,573 件を取り込む時間：

| 版 | やり方 | 全件の時間 | 速度 | 最大メモリ |
|---|---|---|---|---|
| [v1](src/import-naive.ts) | CSV を丸ごと読み込み、1 件ずつ INSERT | 約 5 時間（計算上） | 88 件/秒 | 1,453 MB |
| [v2](src/import-v2.ts) | ストリーミング処理 + 1,000 件ずつまとめて INSERT | 約 7 分（415.26 秒） | 4,220 件/秒 | 562 MB |
| [v3](src/import-v3.ts) | `LOAD DATA LOCAL INFILE` で DB に直接読み込ませる | **約 15 秒（15.11 秒）** | 115,976 件/秒 | 154 MB |

- v1 は全件を測っていません。10,000 件の計測結果からの計算です（[v1](#v1素直に書いた遅い版)を参照）
- v2 は Node.js のヒープ上限を 512 MB にして測った値です
- v2 と v3 で取り込んだテーブルは、`CHECKSUM TABLE`（テーブルの中身から計算する値）が同じ値（967527444）になり、中身が一致することを確かめています

## 使うデータ

- 東京都 住居表示-住居マスター（`mt_rsdtdsp_rsdt_pref13.csv`）
  - 「○丁目○番○号」の単位の住所の一覧です
- 件数：1,752,573 件（ヘッダー行を除く）
- 大きさ：約 150 MB、UTF-8、改行は CRLF
- 計測に使ったファイルの日付：2025-10-27

## 動かし方

必要なもの：Node.js 22、Docker（Docker Compose）、curl、unzip

```bash
npm install
cp .env.example .env     # DB の接続先（compose.yaml の MySQL に合わせてある）
npm run db:up            # MySQL 8.4 を起動（ポート 3307）
npm run download         # データを data/ にダウンロード
npx prisma generate      # Prisma のクライアントを作る
npx prisma migrate deploy   # テーブルを作る

npm run import:naive -- --limit 10000   # v1（遅いので件数を区切って試す）
npm run import:v2                       # v2（全件）
npm run import:v3                       # v3（全件）
```

オプション：

- v2：`--batch 件数`（1 回にまとめる件数、既定 1,000）
- v3：`--chunk-mb 大きさ`（1 回の LOAD DATA で送る大きさ、既定 4 MB）

## 計測環境

- CPU：AMD Ryzen 7 5700X（8 コア 16 スレッド）
- メモリ：WSL2 に割り当てられたメモリ 31 GB
- Windows の WSL2 上で Node.js 22 を実行し、MySQL 8.4 は Rancher Desktop（Docker）で実行

## 各版の内容

### v1：素直に書いた遅い版

[src/import-naive.ts](src/import-naive.ts)

- CSV を丸ごとメモリに読み込んでから、Prisma の `create` で 1 件ずつ INSERT します

| 件数 | 時間 | 速度 | 最大メモリ |
|---|---|---|---|
| 1,000 | 23.26 秒 | 43 件/秒 | 1,337 MB |
| 10,000 | 114.06 秒 | 88 件/秒 | 1,453 MB |

課題：

- 1 件ごとに DB と往復するため、1 件あたり約 10 ミリ秒かかります（上の 2 回の差から計算）
- 時間には CSV 全体を読み込む十数秒が含まれるので、件数が少ないほど速度の数字が下がります
- CSV（約 150 MB）を丸ごと読み込むため、件数が少なくてもメモリを 1.3 GB 以上使います
- この速さのまま全件を入れると、5 時間ほどかかる計算です

### v2：ストリーミング処理 + まとめて INSERT

[src/import-v2.ts](src/import-v2.ts)

- CSV を少しずつ読みながら処理します（ストリーミング処理）。CSV を読むだけなら、メモリは 7 MB 程度で一定です
- Prisma の `createMany` で 1,000 件ずつまとめて INSERT し、DB との往復を 1,000 分の 1 にしました

| 条件 | 時間 | 速度 | 最大メモリ |
|---|---|---|---|
| ヒープ上限なし | 409.61 秒 | 4,279 件/秒 | 1,273 MB |
| ヒープ上限 512 MB | 415.26 秒 | 4,220 件/秒 | 562 MB |

#### 見つけた問題：少しずつ読んでいるのにメモリが 2 GB を超えた

- 最初の v2 は、全件で最大メモリが 2,123 MB になりました
- ヒープスナップショット（その時点でメモリに残っているものの記録）を撮って参照元をたどると、Prisma のデバッグ用部品（`@prisma/debug`）が、**ログを出さない設定でも直近 100 回分の SQL と引数を取っておいていました**
- まとめて INSERT すると 1 回分の引数が大きい（1,000 件 × 22 列）ため、これだけで約 200 MB を使っていました
- 対処として、INSERT のたびに `@prisma/debug` の `clearLogs()` を呼んで、履歴を消すようにしました
- 残りの使用量（強制的に GC した直後で約 243 MB）は、件数が増えても一定でした。増え続けるメモリリークではありません。中身は Prisma 内部の SQL の組み立て結果ですが、何のために持っているのかは突き止められていません
- ヒープ上限なしで最大メモリが 1,273 MB になるのは、GC（使い終わったメモリの片付け）が後回しにされている分です。上限を 512 MB にしても、速度は変わらず完走しました

#### 1 回にまとめる件数の比較

| まとめる件数 | ヒープ上限 | 結果 | 時間 | 速度 | 最大メモリ |
|---|---|---|---|---|---|
| 1,000 件 | 512 MB | 完走 | 415.26 秒 | 4,220 件/秒 | 562 MB |
| 2,000 件 | 512 MB | メモリ不足で停止（88,000 件の時点） | - | - | - |
| 3,000 件 | 512 MB | メモリ不足で停止（48,000 件の時点） | - | - | - |
| 2,000 件 | 1 GB | 完走 | 428.33 秒 | 4,092 件/秒 | 1,007 MB |
| 3,000 件 | 1 GB | 完走 | 437.04 秒 | 4,010 件/秒 | 1,059 MB |

- まとめる件数を増やしても速くはならず、わずかに遅くなりました。DB との往復を減らす効果は 1,000 件で頭打ちになっていると考えられます
- 件数を増やすとメモリが足りなくなるのは、上の「Prisma 内部に残る分」が 1 回分の大きさに比例して増えるためと考えられます（直接は測っていません）
- 1,000 件ずつが、メモリと速さの釣り合いがいちばんよい結果でした
- 2,000 件と 3,000 件の取り込み結果も、チェックサムが v3 と一致しました

### v3：LOAD DATA LOCAL INFILE

[src/import-v3.ts](src/import-v3.ts)

- MySQL の `LOAD DATA LOCAL INFILE` で、CSV を DB に直接読み込ませます。1 行ずつの SQL を組み立てないので、v2 の約 27 倍の速さです
- Prisma は `LOAD DATA LOCAL` に対応していないので、v3 だけ mariadb ドライバーを直接使います
- 空文字は `NULLIF` で NULL に変えて、v1・v2 と同じ結果になるようにしています

#### 見つけた問題 1：改行コード

- ABR の CSV は改行が CRLF でした。v2 で使った csv-parse は自動で処理していましたが、LOAD DATA では `LINES TERMINATED BY '\r\n'` と指定しないと、最後の列に `\r` が残ります

#### 見つけた問題 2：一度に送れる量の上限

- ファイル全体（約 150 MB）を 1 回で送ると、`max_allowed_packet`（1 回に送れる量の上限、この環境では 64 MB）を超えて DB に断られました
- 上限を上げる方法もありますが、もっと大きなファイルでまた失敗します。そこで、CSV を行の切れ目で区切って、何回かに分けて送るようにしました
- 一時ファイルは作らず、ドライバーの `infileStreamFactory` に区切ったデータを渡しています

#### 区切る大きさの比較（全件）

| 区切る大きさ | LOAD DATA の回数 | 時間 | 最大メモリ |
|---|---|---|---|
| 4 MB | 36 回 | 15.11 秒 | 154 MB |
| 16 MB | 9 回 | 15.09〜15.21 秒（3 回計測） | 229〜256 MB |
| 32 MB | 5 回 | 15.89 秒 | 328 MB |
| 48 MB | 3 回 | 17.00 秒 | 461 MB |

速さはほとんど変わらず、小さいほどメモリが少ないので、既定値を 4 MB にしました。
