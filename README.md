# abr-batch

デジタル庁の「アドレス・ベース・レジストリ」（住所の公式データ）を MySQL に取り込むバッチです。
素直に書いた遅い版から始めて、段階的に速くしていく過程と、その計測結果を残します。

## 使うデータ

- 東京都 住居表示-住居マスター（`mt_rsdtdsp_rsdt_pref13.csv`）
- 件数：1,752,573 件（ヘッダー行を除く。2025-10-27 版の CSV で数えたもの）

## 動かし方

```bash
npm install
npm run db:up            # MySQL 8.4 を起動（ポート 3307）
npm run download         # データを data/ にダウンロード
npx prisma migrate deploy   # テーブルを作成
npm run import:naive -- --limit 10000   # v1（遅い版。件数を区切って試す）
npm run import:v2                       # v2（全件）
npm run import:v3                       # v3（全件、LOAD DATA）
```

## 計測結果

計測環境：Windows の WSL2 上の Node.js 22、MySQL 8.4 は Rancher Desktop（Docker）上で実行。

| 版 | やり方 | 件数 | 時間 | 速度 | 最大メモリ |
|---|---|---|---|---|---|
| v1 | CSV を丸ごと読み込み、1件ずつ INSERT | 1,000 | 23.26 秒 | 43 件/秒 | 1,337 MB |
| v1 | 同上 | 10,000 | 114.06 秒 | 88 件/秒 | 1,453 MB |
| v2 | ストリーミング処理 + 1,000件ずつ createMany | 1,752,573（全件） | 409.61 秒 | 4,279 件/秒 | 1,273 MB |
| v2 | 同上、Node.js のヒープ上限 512 MB | 1,752,573（全件） | 415.26 秒 | 4,220 件/秒 | 562 MB |
| v3 | LOAD DATA LOCAL INFILE（4 MB ずつ送る） | 1,752,573（全件） | 15.11 秒 | 115,976 件/秒 | 154 MB |

v1 の課題：

- 1件ごとに DB と往復するため、1件あたり約 10 ミリ秒かかる（上の2回の差から計算）
- CSV（約 150 MB）を丸ごと読み込むため、件数が少なくてもメモリを 1.3 GB 以上使う
- この速さのまま全件（約 175 万件）を入れると、5 時間ほどかかる計算になる（実測ではない）

v2 でやったこと：

- CSV を少しずつ読みながら処理する（ストリーミング処理）。CSV の読み込みだけなら、使うメモリは 7 MB 程度で一定
- 1,000 件ずつまとめて INSERT して、DB との往復を 1,000 分の 1 にした。速度は v1 の約 50 倍
- 全件で計測して、v1 の 5 時間（計算上）が約 7 分になった

v2 で見つけた問題と対処：

- 最初の v2 は、全件で最大メモリが 2,123 MB になった。ヒープスナップショット（その時点でメモリに残っている物の記録）を調べると、Prisma のデバッグ用部品（`@prisma/debug`）が、ログを出さない設定でも直近 100 回分の SQL と引数を取っておいていた
- まとめて INSERT すると 1 回分の引数が大きい（1,000 件 × 22 列）ため、これだけで約 200 MB を使っていた
- `@prisma/debug` の `clearLogs()` を INSERT のたびに呼んで、履歴を消すようにした
- 残りの使用量（強制的に GC した直後で約 243 MB）は件数が増えても一定で、増え続けるメモリリークではない。中身は Prisma 内部の SQL 組み立て結果だが、何のために持っているかは突き止められていない
- 最大メモリの 1,273 MB の多くは、GC（使い終わったメモリの片付け）が後回しになっている分。ヒープ上限を 512 MB にしても速度は変わらず完走した

まとめる件数の比較（ヒープ上限 512 MB、全件）：

| 1 回にまとめる件数 | 結果 |
|---|---|
| 1,000 件 | 完走（415.26 秒、最大メモリ 562 MB） |
| 2,000 件 | メモリ不足で停止（88,000 件を入れたところ） |
| 3,000 件 | メモリ不足で停止（48,000 件を入れたところ） |

まとめる件数を増やすと、Prisma の内部に残るメモリも増えるため、512 MB では足りなくなる。

v3 でやったこと：

- MySQL の `LOAD DATA LOCAL INFILE` で、CSV を DB に直接読み込ませた。全件が約 15 秒で、v2 の約 27 倍
- Prisma は `LOAD DATA LOCAL` に対応していないので、v3 だけ mariadb ドライバーを直接使う
- v2 と v3 で取り込んだテーブルの `CHECKSUM TABLE` が同じ値（967527444）になり、中身が一致することを確認した

v3 で見つけた問題と対処：

- ABR の CSV は改行が CRLF だった。v2 の csv-parse は自動で処理していたが、LOAD DATA では `LINES TERMINATED BY '\r\n'` と指定しないと、最後の列に `\r` が残る
- ファイル全体（約 150 MB）を 1 回で送ると、`max_allowed_packet`（1 回に送れる量の上限、既定 64 MB）を超えて DB に断られた。上限を上げる方法もあるが、もっと大きなファイルでまた落ちるので、CSV を行の切れ目で区切って何回かに分けて送るようにした。一時ファイルは作らず、ドライバーの `infileStreamFactory` に区切ったデータを渡している

区切る大きさの比較（全件）：

| 区切る大きさ | LOAD DATA の回数 | 時間 | 最大メモリ |
|---|---|---|---|
| 4 MB | 36 回 | 15.11 秒 | 154 MB |
| 16 MB | 9 回 | 15.09〜15.21 秒（3 回計測） | 229〜256 MB |
| 32 MB | 5 回 | 15.89 秒 | 328 MB |
| 48 MB | 3 回 | 17.00 秒 | 461 MB |

速さはほとんど変わらず、小さいほどメモリが少ないので、既定値は 4 MB にした。
