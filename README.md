# abr-batch

デジタル庁の「アドレス・ベース・レジストリ」（住所の公式データ）を MySQL に取り込むバッチです。
素直に書いた遅い版から始めて、計測しながら段階的に速くしていった過程を残しています。
後半の v4 では、`LOAD DATA` を使えない場面を想定して、CSV と DB の差分だけを反映する差分更新を作りました。

## 結果のまとめ

東京都の住居表示データ 1,752,573 件を、空のテーブルに取り込む時間：

| 版 | やり方 | 全件の時間 | 速度 | 最大メモリ |
|---|---|---|---|---|
| [v1](src/import-naive.ts) | CSV を丸ごと読み込み、1 件ずつ INSERT | 約 5 時間（計算上） | 88 件/秒 | 1,453 MB |
| [v2](src/import-v2.ts) | ストリーミング処理 + 1,000 件ずつまとめて INSERT（Prisma） | 約 7 分（415.26 秒） | 4,220 件/秒 | 562 MB |
| [v3](src/import-v3.ts) | `LOAD DATA LOCAL INFILE` で DB に直接読み込ませる | **約 15 秒（15.11 秒）** | 115,976 件/秒 | 154 MB |

- v1 は全件を測っていません。10,000 件の計測結果からの計算です（[v1](#v1素直に書いた遅い版)を参照）
- v2 は Node.js のヒープ上限を 512 MB にして測った値です
- v2 と v3 で取り込んだテーブルは、`CHECKSUM TABLE`（テーブルの中身から計算する値）が同じ値（967527444）になり、中身が一致することを確かめています

既存のテーブルに差分だけを反映する [v4](src/sync-v4.ts)（`INSERT ... ON DUPLICATE KEY UPDATE`、1,000 件ずつ）：

| 場面 | 時間 |
|---|---|
| 約 6,000 件の差分（全件を比べて、差分だけ反映） | 20.36 秒 |
| 全件を更新 | 93.05 秒 |
| 全件を追加（空のテーブルから） | 66.38 秒 |

## 見どころ

計測と調査で見つけた問題と、その対処です。詳しくは各版の説明にあります。

| 見つけた問題 | 対処 | 版 |
|---|---|---|
| 少しずつ読んでいるのに、メモリが 2 GB を超えた。原因は、Prisma のデバッグ用部品が、ログを出さない設定でも直近 100 回分の SQL と引数を取っておく作りだったこと | ヒープスナップショットで原因を特定し、`clearLogs()` で毎回消す | [v2](#v2ストリーミング処理--まとめて-insert) |
| ファイル全体を 1 回の `LOAD DATA` で送ると、DB に断られる（`max_allowed_packet` を超える） | CSV を行の切れ目で区切って、何回かに分けて送る | [v3](#v3load-data-local-infile) |
| 配布 CSV の改行が CRLF で、`LOAD DATA` だと最後の列に `\r` が残る | 行の区切りを `'\r\n'` と指定する | [v3](#v3load-data-local-infile) |
| 配布 CSV が、主キー順に並んでいない（374 か所） | 比べる前に毎回並べ替え、読みながら順番もチェックする | [v4](#v4差分更新load-data-を使えない場面向け) |
| キーセット方式で `(a, b, c, d, e) > (...)` と書くと、1 ページの読み込みが 1,000 倍以上遅くなる | `a > ? OR (a = ? AND b > ?) OR ...` に展開する | [v4](#v4差分更新load-data-を使えない場面向け) |

## 使うデータ

- 東京都 住居表示-住居マスター（`mt_rsdtdsp_rsdt_pref13.csv`）
  - 「○丁目○番○号」の単位の住所の一覧です
- 件数：1,752,573 件（ヘッダー行を除く）
- 大きさ：約 150 MB、UTF-8、改行は CRLF
- 計測に使ったファイルの日付：2025-10-27

## 動かし方

必要なもの：Node.js 22、Docker（Docker Compose）、curl、unzip、sort

```bash
npm install
cp .env.example .env     # DB の接続先（compose.yaml の MySQL に合わせてある）
npm run db:up            # MySQL 8.4 を起動（ポート 3307）
npm run download         # データを data/ にダウンロード
npx prisma generate      # Prisma のクライアントを作る
npx prisma migrate deploy   # テーブルを作る

npm run import:naive -- --limit 10000   # v1（遅いので件数を区切って試す）
npm run import:v2                       # v2（全件）
npm run import:v3                       # v3（全件）

npm run sync:v4 -- --dry-run            # v4（差分を調べてログだけ出す）
npm run sync:v4                         # v4（差分を反映する）
bash scripts/make-test-csv.sh           # v4 の確認用に、一部を変えた CSV を作る
npm run sync:v4 -- data/test_modified.csv
```

オプション：

- v2：`--batch 件数`（1 回にまとめる件数、既定 1,000）
- v3：`--chunk-mb 大きさ`（1 回の LOAD DATA で送る大きさ、既定 4 MB）
- v4：`--dry-run`（DB を変えずにログだけ出す）、`--batch 件数`（既定 1,000）、`--max-delete-ratio 割合`（既定 0.1）、`--force`（安全装置を無視する）

## 各版の内容

### v1：素直に書いた遅い版

[src/import-naive.ts](src/import-naive.ts)

- CSV を丸ごとメモリに読み込んでから、Prisma の `create` で 1 件ずつ INSERT します

| 件数 | 時間 | 速度 | 最大メモリ |
|---|---|---|---|
| 1,000 | 23.26 秒 | 43 件/秒 | 1,337 MB |
| 10,000 | 114.06 秒 | 88 件/秒 | 1,453 MB |

課題：

- 1 件ごとに DB と往復するため、1 件あたり約 10 ミリ秒かかります（上の 2 回の差から計算）
- 時間には CSV 全体を読み込む十数秒が含まれるので、件数が少ないほど速度の数字が下がります
- CSV（約 150 MB）を丸ごと読み込むため、件数が少なくてもメモリを 1.3 GB 以上使います
- この速さのまま全件を入れると、5 時間ほどかかる計算です

### v2：ストリーミング処理 + まとめて INSERT

[src/import-v2.ts](src/import-v2.ts)

- CSV を少しずつ読みながら処理します（ストリーミング処理）。CSV を読むだけなら、メモリは 7 MB 程度で一定です
- Prisma の `createMany` で 1,000 件ずつまとめて INSERT し、DB との往復を 1,000 分の 1 にしました

| 条件 | 時間 | 速度 | 最大メモリ |
|---|---|---|---|
| 最初の版（下の問題に対処する前）、ヒープ上限なし | 438.47 秒 | 3,997 件/秒 | 2,123 MB |
| 対処後、ヒープ上限なし | 409.61 秒 | 4,279 件/秒 | 1,273 MB |
| 対処後、ヒープ上限 512 MB | 415.26 秒 | 4,220 件/秒 | 562 MB |

#### 見つけた問題：少しずつ読んでいるのにメモリが 2 GB を超えた

- 最初の v2 は、全件で最大メモリが 2,123 MB になりました
- ヒープスナップショット（その時点でメモリに残っているものの記録）を撮って参照元をたどると、Prisma のデバッグ用部品（`@prisma/debug`）が、**ログを出さない設定でも直近 100 回分の SQL と引数を取っておいていました**
- まとめて INSERT すると 1 回分の引数が大きい（1,000 件 × 22 列）ため、これだけで約 200 MB を使っていました
- 対処として、INSERT のたびに `@prisma/debug` の `clearLogs()` を呼んで、履歴を消すようにしました
- 残りの使用量（強制的に GC した直後で約 243 MB）は、件数が増えても一定でした。増え続けるメモリリークではありません。中身は Prisma 内部の SQL の組み立て結果ですが、何のために持っているのかは突き止められていません
- 対処後の最大メモリは、ヒープ上限なしで 1,273 MB になりました（対処前は 2,123 MB）。残る 243 MB を除いた分は、GC（使い終わったメモリの片付け）が後回しにされている分です。上限を 512 MB にしても、速度は変わらず完走しました

#### 1 回にまとめる件数の比較

| まとめる件数 | ヒープ上限 | 結果 | 時間 | 速度 | 最大メモリ |
|---|---|---|---|---|---|
| 1,000 件 | 512 MB | 完走 | 415.26 秒 | 4,220 件/秒 | 562 MB |
| 2,000 件 | 512 MB | メモリ不足で停止（88,000 件の時点） | - | - | - |
| 3,000 件 | 512 MB | メモリ不足で停止（48,000 件の時点） | - | - | - |
| 2,000 件 | 1 GB | 完走 | 428.33 秒 | 4,092 件/秒 | 1,007 MB |
| 3,000 件 | 1 GB | 完走 | 437.04 秒 | 4,010 件/秒 | 1,059 MB |

- まとめる件数を増やしても速くはならず、わずかに遅くなりました。DB との往復を減らす効果は 1,000 件で頭打ちになっていると考えられます
- 件数を増やすとメモリが足りなくなるのは、上の「Prisma 内部に残る分」が 1 回分の大きさに比例して増えるためと考えられます（直接は測っていません）
- 1,000 件ずつが、メモリと速さの釣り合いがいちばんよい結果でした
- 2,000 件と 3,000 件の取り込み結果も、チェックサムが v3 と一致しました

### v3：LOAD DATA LOCAL INFILE

[src/import-v3.ts](src/import-v3.ts)

- MySQL の `LOAD DATA LOCAL INFILE` で、CSV を DB に直接読み込ませます。1 行ずつの SQL を組み立てないので、v2 の約 27 倍の速さです
- Prisma は `LOAD DATA LOCAL` に対応していないので、mariadb ドライバーを直接使います
- 空文字は `NULLIF` で NULL に変えて、v1・v2 と同じ結果になるようにしています

#### 見つけた問題 1：改行コード

- ABR の CSV は改行が CRLF でした。v2 で使った csv-parse は自動で処理していましたが、LOAD DATA では `LINES TERMINATED BY '\r\n'` と指定しないと、最後の列に `\r` が残ります

#### 見つけた問題 2：一度に送れる量の上限

- ファイル全体（約 150 MB）を 1 回で送ると、`max_allowed_packet`（1 回に送れる量の上限、この環境では 64 MB）を超えて DB に断られました
- 上限を上げる方法もありますが、もっと大きなファイルでまた失敗します。そこで、CSV を行の切れ目で区切って、何回かに分けて送るようにしました
- 一時ファイルは作らず、ドライバーの `infileStreamFactory` に区切ったデータを渡しています

#### 区切る大きさの比較（全件）

| 区切る大きさ | LOAD DATA の回数 | 時間 | 最大メモリ |
|---|---|---|---|
| 4 MB | 36 回 | 15.11 秒 | 154 MB |
| 16 MB | 9 回 | 15.09〜15.21 秒（3 回計測） | 229〜256 MB |
| 32 MB | 5 回 | 15.89 秒 | 328 MB |
| 48 MB | 3 回 | 17.00 秒 | 461 MB |

速さはほとんど変わらず、小さいほどメモリが少ないので、既定値を 4 MB にしました。

### v4：差分更新（LOAD DATA を使えない場面向け）

[src/sync-v4.ts](src/sync-v4.ts)

空のテーブルに全件を入れるなら v3 の `LOAD DATA` が最速です。ただ、実際の運用では次のような場面があります。

- 既存のテーブルに、変わった分だけを反映したい（全件を入れ直すと、その間は参照できない）
- 何が追加・更新・削除されたかを記録に残したい
- 権限や設定の都合で `LOAD DATA LOCAL` を使えない

そこで、CSV と DB を比べて、差分だけを反映するバッチを作りました。

#### 仕組み

1. CSV を主キー順に並べ替える（OS の `sort` コマンドを使う）
2. DB を主キー順に 1,000 件ずつ読む（キーセット方式：前回読んだ最後のキーより後ろを読む）
3. 両方を先頭から同時に読み進めて比べる（マージ比較）。メモリは件数によらずほぼ一定
   - CSV にだけある行 → 追加
   - 両方にあって値が違う行 → 更新
   - DB にだけある行 → 削除
4. 追加と更新は `INSERT ... ON DUPLICATE KEY UPDATE`、削除は `DELETE ... WHERE (主キー) IN (...)` で、1,000 件ずつ反映する
5. 実行ログ・変更ログ・SQL ログを `logs/` に残す（下の「ログ」を参照）

#### 安全装置

- `--dry-run` を付けると、DB を変えずにログだけ出します
- CSV の件数が DB より 10% 以上少ないときは、何もせずに止めます。CSV が途中で切れていたときに、大量に削除してしまわないためです（`--max-delete-ratio` で割合を変えられます。CSV が正しいと確かめたうえで、`--force` で無視することもできます）

#### 見つけた問題 1：配布 CSV は主キー順に並んでいない

- ほぼ主キー順ですが、374 か所で `rsdt2_id` が空の行が、空でない行より後ろに来ていました
- マージ比較は両方が同じ順に並んでいることが前提なので、配布ファイルの並びには頼らず、毎回並べ替えています。並べ替えの順が DB の `ORDER BY` と食い違ったときに気づけるよう、読みながら順番もチェックしています

#### 見つけた問題 2：キーセット方式の書き方で、1 ページの読み込みが 1,000 倍以上遅くなる

`WHERE (主キーの 5 列) > (前回の最後のキー)` と書くと、MySQL 8.4 ではインデックスの範囲検索が使われず、ページを読むたびに先頭から読み直していました。テーブルの後ろの方のページを `EXPLAIN ANALYZE` で比べた結果です。

| 書き方 | 1 ページ（1,000 件）の時間 |
|---|---|
| `(a, b, c, d, e) > (?, ?, ?, ?, ?)` | 1,058 ミリ秒 |
| `a >= ? AND (a, b, c, d, e) > (?, ?, ?, ?, ?)` | 24 ミリ秒 |
| `a > ? OR (a = ? AND b > ?) OR ...`（OR に展開） | 0.8 ミリ秒 |

OR に展開した書き方を使っています。

#### 動作の確認

確認用に、元の CSV から 1,752 行を削除、3,505 行を変更、927 行を追加した CSV と、全行を変更した CSV を作りました。どちらも大きいのでリポジトリには入れず、作るためのシェルスクリプト（[scripts/make-test-csv.sh](scripts/make-test-csv.sh)）を置いています。規則が決まっているので、何度作っても同じ中身になります。

| 確認したこと | 結果 |
|---|---|
| 差分の件数 | 追加 927、更新 3,505、削除 1,752 で、作った数と一致 |
| `--dry-run` | DB のチェックサムが変わらない |
| v4 で反映した結果 | 同じ CSV を v3 で入れ直した結果とチェックサムが一致（1329018278） |
| もう一度 v4 を実行 | 変更 0 件 |
| 元の CSV で v4 を実行 | 元のチェックサム（967527444）に戻る |
| 先頭 10 万行だけの CSV | 安全装置で止まり、DB は変わらない |
| DB に接続できない | 実行ログに `FAILED` とエラー内容が残り、終了コードが 1 になる |

#### 計測結果（全件 1,752,573 件）

| 場面 | 時間 | 速度 | 最大メモリ | 変更ログ | SQL ログ |
|---|---|---|---|---|---|
| 変更なし（比べるだけ、`--dry-run`） | 20.37 秒 | 86,029 件/秒 | 168 MB | まとめの 1 行のみ | 1,754 行、14 KB |
| 約 6,000 件の差分（上の確認用 CSV） | 20.36 秒 | 86,111 件/秒 | 170 MB | 97 KB | 1,761 行、16 KB |
| 全件を更新 | 93.05 秒 | 18,835 件/秒 | 198 MB | 6.3 MB | 3,507 行、38 KB |
| 全件を追加（空のテーブルから） | 66.38 秒 | 26,400 件/秒 | 222 MB | 20 MB | 1,755 行、20 KB |

- ログの大きさは gzip 圧縮後の値です
- 差分が少なければ、全件を比べても約 20 秒で終わります
- 全件を追加する場面でも約 1 分でした。同じ 1,000 件ずつの INSERT でも、Prisma の `createMany` を使った v2（約 7 分）よりずっと速く、Prisma の処理の重さが分かります
- 約 6,000 件の差分のとき、SQL の実行時間の合計は約 5 秒でした。全体（約 20 秒）の残りは、CSV の並べ替えと比較の時間です（SQL ログの `ms` を合計して確認）

#### ログ

ログは `logs/` に 3 種類出します。時刻とファイル名は日本時間です。

| ログ | ファイル | 中身 |
|---|---|---|
| 実行ログ | `batch.log`（追記） | 開始と終了を 1 行ずつ。引数、成功か失敗か、処理時間、件数、エラー内容 |
| 変更ログ | `sync-日時.jsonl.gz` | 追加・更新・削除した行（1 行に 1 件の JSON、gzip 圧縮） |
| SQL ログ | `sql-日時.jsonl.gz` | 実行した SQL、かかった時間、件数（1 文に 1 行、gzip 圧縮） |

実行ログの例（成功と、安全装置で止まったとき。`file` のパスは置き換えています）：

```
2026-11-19T15:18:22.769+09:00 [START] batch="sync:v4" pid=35544 args="data/test_modified.csv" file="/path/to/abr-batch/data/test_modified.csv" dryRun=false batchSize=1000 sqlLog="logs/sql-20261119-151822.jsonl.gz"
2026-11-19T15:18:43.659+09:00 [END] batch="sync:v4" pid=35544 status="SUCCESS" sec=20.89 compared=1750821 unchanged=1747316 insert=927 update=3505 delete=1752 changeLog="logs/sync-20261119-151822.jsonl.gz"
2026-11-19T15:19:05.855+09:00 [END] batch="sync:v4" pid=35684 status="FAILED" sec=0.27 error="Error: CSV の件数が DB より 10% 以上少ないので止めました。…" compared=0 unchanged=0 insert=0 update=0 delete=0
```

- 異常終了しても残るよう、同期書き込みで追記します
- DB に接続できなかったときも `FAILED` とエラー内容が残ります。失敗したときの終了コードは 1 なので、cron などから実行したときに失敗を検知できます

変更ログの例（更新）：

```json
{"at":"2026-11-19T15:18:28.618+09:00","op":"update","key":{"lg_code":"131016","machiaza_id":"0004001","blk_id":"009","rsdt_id":"004","rsdt2_id":""},"changes":{"remarks":[null,"テスト更新"]}}
```

- 追加は追加した行（`after`）、更新は変わった列の変更前と変更後（`changes`）、削除は削除する前の行（`before`）を残します
- 最後の行に、件数のまとめ（`summary`）を書きます

SQL ログの例（DELETE）：

```json
{"at":"2026-11-19T15:18:35.303+09:00","conn":"writer","ms":93.8,"affectedRows":1000,"params":5000,"sql":"DELETE FROM mt_rsdtdsp_rsdt WHERE (`lg_code`, `machiaza_id`, `blk_id`, `rsdt_id`, `rsdt2_id`) IN ((?, ?, ?, ?, ?) ×1000)"}
```

- 引数の値は書きません。1 回で最大 22,000 個になり、ログが巨大になるためです。値は変更ログに残っています
- 同じ形のプレースホルダーの並びは `(?, ?, ?, ?, ?) ×1000` のように縮めて書きます
- `INSERT ... ON DUPLICATE KEY UPDATE` の `affectedRows` は、MySQL の仕様で追加 1 件を 1、更新 1 件を 2 と数えます（例：1,000 件のうち 791 件が更新なら 1,791）

ログは圧縮してあるので、`zgrep` や `zcat` で探せます。

```bash
grep FAILED logs/batch.log                                # 失敗した実行
zgrep -c '"op":"delete"' logs/sync-*.jsonl.gz              # 削除した件数
zgrep '"oaza_cho":"九段南"' logs/sync-*.jsonl.gz            # 特定の住所の変更を探す
zcat logs/sync-20261119-151822.jsonl.gz | tail -1          # 件数のまとめ
zgrep '"error"' logs/sql-*.jsonl.gz                       # 失敗した SQL
```

#### ログの圧縮

最初は変更ログを圧縮せずに書いていましたが、変更が大量にあるとログが大きくなりすぎたので、gzip で圧縮するようにしました（SQL ログを入れる前のコードで比べた値です）。

| 場面 | 圧縮前 | 圧縮後 | 時間（圧縮前 → 圧縮後） |
|---|---|---|---|
| 約 6,000 件の差分 | 約 2.1 MB | 96 KB | 19.87 → 20.27 秒 |
| 全件を更新 | 約 345 MB | 6.3 MB | 90.59 → 92.58 秒 |
| 全件を追加 | 約 967 MB | 20 MB | 59.04 → 70.93 秒 |

ログは 20〜50 分の 1 になり、時間の増え方は全件追加でも 12 秒ほどでした。
