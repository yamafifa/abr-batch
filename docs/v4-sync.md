# v4：差分更新（LOAD DATA を使えない場面向け）

[src/sync-v4.ts](../src/sync-v4.ts)

空のテーブルに全件を入れるなら v3 の `LOAD DATA` が最速です。ただ、実際の運用では次のような場面があります。

- 既存のテーブルに、変わった分だけを反映したい（全件を入れ直すと、その間は参照できない）
- 何が追加・更新・削除されたかを記録に残したい
- 権限や設定の都合で `LOAD DATA LOCAL` を使えない

そこで、CSV と DB を比べて、差分だけを反映するバッチを作りました。

## 実行コマンド

準備（DB の起動、データのダウンロード、テーブル作成）は、README の「[動かし方](../README.md#動かし方)」を参照してください。v3 などで全件を入れておくと、差分更新を試せます（空のテーブルでも動き、その場合は全件を追加します）。

```bash
npm run sync:v4 -- --dry-run                  # 差分を調べてログだけ出す（DB は変えない）
npm run sync:v4                               # 配布 CSV（data/mt_rsdtdsp_rsdt_pref13.csv）と比べて反映する

bash scripts/make-test-csv.sh                 # 確認用 CSV を data/ に作る
npm run sync:v4 -- data/test_modified.csv     # 約 6,000 件の差分を反映する
npm run sync:v4                               # 元の CSV に戻す
npm run sync:v4 -- data/test_all_updated.csv  # 全件を更新する
npm run sync:v4                               # 元の CSV に戻す
```

- オプション：`--batch 件数`（1 回に反映する件数、既定 1,000）、`--max-delete-ratio 割合`（既定 0.1）、`--force`（安全装置を無視する）
- 終わると、変更ログと SQL ログのパスを表示します。ログの中身と探し方は [logs.md](logs.md) にあります

## 計測結果（全件 1,752,573 件）

| 場面 | 時間 | 速度 | 最大メモリ | 変更ログ | SQL ログ |
|---|---|---|---|---|---|
| 変更なし（比べるだけ、`--dry-run`） | 20.37 秒 | 86,029 件/秒 | 168 MB | まとめの 1 行のみ | 1,754 行、14 KB |
| 約 6,000 件の差分（下の「動作の確認」の確認用 CSV） | 20.36 秒 | 86,111 件/秒 | 170 MB | 97 KB | 1,761 行、16 KB |
| 全件を更新 | 93.05 秒 | 18,835 件/秒 | 198 MB | 6.3 MB | 3,507 行、38 KB |
| 全件を追加（空のテーブルから） | 66.38 秒 | 26,400 件/秒 | 222 MB | 20 MB | 1,755 行、20 KB |

- ログの大きさは gzip 圧縮後の値です
- 差分が少なければ、全件を比べても約 20 秒で終わります
- 約 6,000 件の差分のとき、SQL の実行時間の合計は約 5 秒でした。全体（約 20 秒）の残りは、CSV の並べ替えと比較の時間です（SQL ログの `ms` を合計して確認）

## 全件を追加する場面で、v2 より速い理由

全件を追加する場面でも約 1 分で、v2（約 7 分）よりずっと速くなりました。どちらも 1,000 件ずつ INSERT しますが、MySQL の中で使った時間（performance_schema で計測）はほぼ同じで、差のほとんどは Node.js 側にあります。

| | v2 | v4 |
|---|---|---|
| 全体の時間 | 419.52 秒 | 66.95 秒 |
| MySQL の中の時間 | 約 47.5 秒（INSERT 35.55 秒＋準備と後片付け 11.92 秒） | 約 34.1 秒（INSERT 34.12 秒） |
| MySQL の外の時間 | 約 372 秒 | 約 33 秒（CSV の並べ替えと比較を含む） |

- 上の表は、performance_schema を有効にして測り直した値です。そのため、上の計測結果（66.38 秒）とは少し違います
- v2 は Prisma がプリペアドステートメントで送るため、1,000 件ごとに SQL の準備と後片付けもしています
- v2 の MySQL の外の時間が、Prisma のどの処理に使われているかは、まだ突き止めていません

## 仕組み

1. CSV を主キー順に並べ替える（OS の `sort` コマンドを使う）
2. DB を主キー順に 1,000 件ずつ読む（キーセット方式：前回読んだ最後のキーより後ろを読む）
3. 両方を先頭から同時に読み進めて比べる（マージ比較）。メモリは件数によらずほぼ一定
   - CSV にだけある行 → 追加
   - 両方にあって値が違う行 → 更新
   - DB にだけある行 → 削除
4. 追加と更新は `INSERT ... ON DUPLICATE KEY UPDATE`、削除は `DELETE ... WHERE (主キー) IN (...)` で、1,000 件ずつ反映する
5. 実行ログ・変更ログ・SQL ログを `logs/` に残す（[ログ](logs.md)を参照）

## 安全装置

- `--dry-run` を付けると、DB を変えずにログだけ出します
- CSV の件数が DB より 10% 以上少ないときは、何もせずに止めます。CSV が途中で切れていたときに、大量に削除してしまわないためです（`--max-delete-ratio` で割合を変えられます。CSV が正しいと確かめたうえで、`--force` で無視することもできます）

## 見つけた問題 1：配布 CSV は主キー順に並んでいない

- ほぼ主キー順ですが、374 か所で `rsdt2_id` が空の行が、空でない行より後ろに来ていました
- マージ比較は両方が同じ順に並んでいることが前提なので、配布ファイルの並びには頼らず、毎回並べ替えています。並べ替えの順が DB の `ORDER BY` と食い違ったときに気づけるよう、読みながら順番もチェックしています

## 見つけた問題 2：キーセット方式の書き方で、1 ページの読み込みが 1,000 倍以上遅くなる

`WHERE (主キーの 5 列) > (前回の最後のキー)` と書くと、MySQL 8.4 ではインデックスの範囲検索が使われず、ページを読むたびに先頭から読み直していました。テーブルの後ろの方のページを `EXPLAIN ANALYZE` で比べた結果です。

| 書き方 | 1 ページ（1,000 件）の時間 |
|---|---|
| `(a, b, c, d, e) > (?, ?, ?, ?, ?)` | 1,058 ミリ秒 |
| `a >= ? AND (a, b, c, d, e) > (?, ?, ?, ?, ?)` | 24 ミリ秒 |
| `a > ? OR (a = ? AND b > ?) OR ...`（OR に展開） | 0.8 ミリ秒 |

OR に展開した書き方を使っています。

## 動作の確認

確認用に、元の CSV から 1,752 行を削除、3,505 行を変更、927 行を追加した CSV と、全行を変更した CSV を作りました。どちらも大きいのでリポジトリには入れず、作るためのシェルスクリプト（[scripts/make-test-csv.sh](../scripts/make-test-csv.sh)）を置いています。規則が決まっているので、何度作っても同じ中身になります。

| 確認したこと | 結果 |
|---|---|
| 差分の件数 | 追加 927、更新 3,505、削除 1,752 で、作った数と一致 |
| `--dry-run` | DB のチェックサムが変わらない |
| v4 で反映した結果 | 同じ CSV を v3 で入れ直した結果とチェックサムが一致（1329018278） |
| もう一度 v4 を実行 | 変更 0 件 |
| 元の CSV で v4 を実行 | 元のチェックサム（967527444）に戻る |
| 先頭 10 万行だけの CSV | 安全装置で止まり、DB は変わらない |
| DB に接続できない | 実行ログに `FAILED` とエラー内容が残り、終了コードが 1 になる |
