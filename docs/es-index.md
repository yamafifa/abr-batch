# es:index：DB から Elasticsearch の検索用インデックスを作る

[src/es-index.ts](../src/es-index.ts)

- AP（abr-web-rails）の検索は `city LIKE '%町田%' OR ward LIKE '%町田%'` のような部分一致です。前に `%` が付く LIKE は MySQL のインデックスでは速くならないので、毎回 175 万行を全部読んでいました
- そこで、MySQL のデータを Elasticsearch（全文検索のサーバー）にコピーするバッチを作りました。AP は Elasticsearch で探します
- 正本（元になるデータ）は MySQL のままです。Elasticsearch は、いつでも MySQL から作り直せる検索用のコピーです
- 毎回、全件を入れ直します（差分の反映はしません）。AP で編集・削除した内容は、次にこのバッチを実行したときに反映されます

## 実行コマンド

準備（DB の起動、データの取り込み）は、README の「[動かし方](../README.md#動かし方)」を参照してください。`npm run db:up` で Elasticsearch も起動します。

```bash
npm run es:index                  # 全件を 5,000 件ずつ送る
npm run es:index -- --batch 1000  # 1 回に送る件数を変える
```

- 接続先は `.env` の `ES_URL`。無ければ `http://127.0.0.1:9200`
- 公式のクライアント（`@elastic/elasticsearch`）は入れず、Node.js の fetch で REST API を呼んでいます（[src/lib/es.ts](../src/lib/es.ts)）。使う API が 6 つだけなので、新しい部品を増やさないことにしました

## 計測結果（全件 1,752,573 件）

| 1 回に送る件数 | 時間 | 速度 | 最大メモリ |
|---|---|---|---|
| 5,000 件（既定値） | 56.81 秒 | 30,849 件/秒 | 370 MB |

- 件数は、MySQL と Elasticsearch で同じでした（バッチの中で毎回確かめています）
- インデックスの大きさは 162.4 MB でした
- 1 回に送る件数を変えた比較は、まだしていません

|---|---|---|

## 流れ

1. 新しいインデックス `rsdt_日時`（例：`rsdt_20261121-220555`）を作ります。取り込み中は refresh（入れたデータを検索に出す処理）を止めます。1 台で動かしているので、複製は作りません
2. MySQL を主キーの順に 5,000 件ずつ読みます。v4 と同じキーセット方式（前回の最後のキーの続きから読む方法）で、`a > ? OR (a = ? AND b > ?) ...` の形に展開しています
3. Bulk API（複数件を 1 回で登録する API）で送ります。次のページを MySQL から読む間に、前のページを送ります
4. refresh を元に戻してから、MySQL と件数を比べます。合わなければ止めて、作りかけのインデックスを消します
5. 別名 `rsdt` を新しいインデックスに付け替えます。外すのと付けるのを 1 回の API で行うので、AP から見て別名が無くなる瞬間はありません
6. 古いインデックス（`rsdt_` で始まるもの）を消します

AP は別名 `rsdt` だけを見ているので、作り直している間も検索は止まりません。

## インデックスの項目

| 項目 | 型 | 使い道 |
|---|---|---|
| `key` | keyword | 主キー 5 列を `_` でつないだもの（例：`131016_0001001_006_001_`）。並べ替えと、ページ送り（search_after）に使う。ドキュメントの ID も同じ値 |
| `fold.city`・`fold.ward`・`fold.oaza_cho`・`fold.koaza`・`fold.chome` | wildcard | 部分一致の検索。文字をそろえた値（下の「文字のそろえ方」） |
| `fold.blk_num`・`fold.rsdt_num` | keyword | 完全一致の検索。文字をそろえた値 |
| 元の 22 列 | keyword（索引なし） | 画面の表示だけに使う。検索用の索引は作らない |

- `key` の並びが主キーの並びと同じになることを確かめました。主キーの各列は桁数が決まっていて（`blk_id`・`rsdt_id` は 3 桁、`rsdt2_id` は空か 5 桁）、数字しか無いためです
- AP の編集画面の URL（Rails の複合主キーの `to_param`）も同じ形なので、そのままリンクに使えます

### 部分一致に wildcard 型を選んだ理由

- AP の LIKE '%…%' と同じ意味で探せます。結果が MySQL と同じか、件数で比べて確かめられます
- 1 文字の検索（例：「西」）もそのまま使えます。ngram（2 文字ずつに区切る方法）では、1 文字の検索に別の工夫が要ります
- 速さは十分でした。全件で「町田」＋「木曽」が 11〜16 ms、「西」（13 万 7,822 件に当たる）が 73〜113 ms（Elasticsearch の中の時間）
- ngram との比較はしていません

## 見つけた問題：MySQL と Elasticsearch で、当たる件数が違う

最初は、DB の値をそのまま wildcard 型に入れました。すると、件数が MySQL と合わない検索がありました。

| 検索 | MySQL | Elasticsearch |
|---|---|---|
| 丁目「3」 | 238,220 件（「３丁目」に当たる） | 0 件 |
| 町字「ケ」 | 12,254 件 | 4,846 件 |

テーブルの照合順序（文字の比べ方）は `utf8mb4_unicode_ci` です。これは次の違いを同じ文字として扱います（MySQL で確かめた結果）。

| 比べたもの | MySQL の結果 |
|---|---|
| `'3' = '３'`、`'a' = 'Ａ'` | 同じ |
| `'あ' = 'ア'` | 同じ |
| `'は' = 'パ'` | 同じ |
| `'ヶ' = 'ケ'` | 同じ |
| `'ヶ' = 'ヵ'` | 違う |
| `'一' = '1'` | 違う |

Elasticsearch の wildcard 型は文字をそのまま比べます。そこで、入れる側と探す側の両方で、同じように文字をそろえることにしました（[src/lib/fold.ts](../src/lib/fold.ts)）。

### 文字のそろえ方

1. NFKC（全角・半角などをそろえる Unicode の正規化）にかけて、小文字にする
2. NFD（濁点などを分ける正規化）にかけて、濁点・半濁点（U+3099・U+309A）を消す
3. カタカナをひらがなにする
4. 小さい仮名を大きくする（ぁ → あ、ゖ → け など）

ただし、**CJK 互換漢字（U+F900〜U+FAFF など）にはかけません**。NFKC・NFD は互換漢字の「塚」（U+FA10）を普通の「塚」（U+585A）に変えます。しかし、MySQL はこの 2 つを別の文字として扱うので、そろえると件数が合わなくなりました（「塚」で MySQL 14,912 件・4,036 件、Elasticsearch は両方 18,948 件）。

AP（abr-web-rails と abr-web-laravel）にも同じ処理（`RsdtFold`）があります。**直すときはすべてを直します。** DB にある検索対象の値すべて（1,159 種類）で、3 つの処理の結果が同じになることを確かめました。

### 確かめ方

MySQL の LIKE と Elasticsearch で、同じ検索の件数を比べました。検索語は、DB の値に出てくる文字すべてと、2 文字の並びから無作為に 300 個ずつ、それに全角・かなの例です。

| | 比べた数 | 合わなかった数 |
|---|---|---|
| そろえる前 | — | 丁目「3」、町字「ケ」など（上の表） |
| 互換漢字もそろえていたとき | 914 | 3（互換漢字の「塚」2 つ、半角の「ﾊﾟ」） |
| 今の形 | 914 | 1（半角の「ﾊﾟ」） |

### 分かっていること・分かっていないこと

- **半角の「ﾊﾟ」は合いません。** MySQL は「ﾊ」と「ﾟ」の 2 文字として探して 0 件になりますが、NFKC が 1 文字の「パ」にするので、Elasticsearch では当たります。半角カナで探すことは少ないと考えて、そのままにしています
- `utf8mb4_unicode_ci` が同じ文字として扱うものを、すべて調べたわけではありません。DB にある文字と、上の例でしか確かめていません

## 書いていて困ったこと

- 濁点の記号を消す正規表現に `\u3099` と書いたつもりが、ファイルに見えない文字そのもの（結合用の濁点）が入っていました。動きは同じですが、読んでも分からないので、`od -c` でバイトを確かめてから `\u3099` の形に直しました
